# CK session script: F29 and F30 (M5.A1, for the owner's sitting M5.O1)

Lane A, 2026-10-16. The step-by-step script for the first owner-assisted Creation Kit
sitting: **F29** (the first POI's crate placed by hand in the CK) and **F30** (the CK opens
our `KitKraftFirstPOI.esm` and saves it again unchanged), what the agent records at each
step, where the files go, and the commands that ingest them afterwards. It refines
`plan/STATUS.md` "Owner next actions" row 12, which stays enough on its own.

**No sitting has happened yet.** Every statement below about the CK's interface (menu
names, dialogs, checkboxes, where it saves) is marked *(unobserved)*: it is our expectation,
to be confirmed or corrected in the sitting and then recorded in `docs/ck-observations.md`
and `docs/ck-parity.md` (ADR 0012). Nothing here comes from the CK's code or files.

## Ground rules

- Owner-assisted: the owner sits at the CK. A computer-use agent may drive it while the
  owner watches; no step assumes the CK runs unattended (binding constraint 3, M5.A4).
- The CK is launched **through MO2 on the `KitKraft Dev` profile**, never `Default`
  (AGENTS.md "Owner's live game is off limits"). It is a black box: no debugger, memory or
  disassembly tool, no Creations upload, no Bethesda.net login.
- The CK writes its saves where it writes them (expected: MO2's `overwrite\` folder when
  launched through MO2 *(unobserved)*). The agent only **copies** them out into `observe\`;
  it writes nothing under the game folder, `Documents\My Games\Starfield` or MO2, except
  F30's input, which goes in through `kit deploy --dev` (ADR 0009).
- Starfield is not running during the sitting.

## Before the sitting (agent, read-only checks)

1. `kit doctor`: the game, the Data dir, MO2 and the `KitKraft Dev` profile are found.
2. Hash the inputs into `hashes.txt`: `Get-FileHash -Algorithm SHA256` on
   `Data\Starfield.esm`, `CreationKit.exe`, `out\poi\KitKraftFirstPOI.esm`.
3. `kit roundtrip out\poi\KitKraftFirstPOI.esm --verify --decode` passes (our input is
   sound before the CK sees it).
4. For F30 only: `kit deploy out\poi\KitKraftFirstPOI.esm C:\Modding\MO2-Starfield --dev
   --profile "KitKraft Dev" --dry-run`, then without `--dry-run` once the owner has read
   the plan. It copies the plugin into the mod `KitKraft Dev - KitKraftFirstPOI` and never
   edits a profile, so the owner enables that mod in MO2 on `KitKraft Dev` (never
   `Default`) for the CK to see the plugin.

## Ingestion (agent, after the sitting)

```powershell
$s = 'C:\Modding\kitkraft\observe\ck-<yyyy-mm-dd>'
Get-FileHash -Algorithm SHA256 $s\F29\*.esm, $s\F30\*.esm | Format-List | Out-File -Append $s\hashes.txt
kit roundtrip $s\F29\ck.esm --verify --decode          # F29 must roundtrip byte-identical
kit roundtrip $s\F30\ck.esm --verify --decode
kit diff $s\F29\kitkraft.esm $s\F29\ck.esm --limit 100000
kit diff $s\F30\kitkraft.esm $s\F30\ck.esm --limit 100000
cargo xtask observe $s\F29 $s\F30                       # report.md in each folder (validate, coverage too)
cargo xtask oracle ck $s\F29 $s\F30                     # observe\ck-oracle\F29\, F30\: classes and verdicts
```

Then M5.A3 classes every difference by hand in a ledger entry of `docs/ck-observations.md`
(format there: `ck-<yyyymmdd>-<nn>`), adds a `[[normalization]]` entry citing it for each
explained class, and reruns `cargo xtask oracle ck ... --check`.
